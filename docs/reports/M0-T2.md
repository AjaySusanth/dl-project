### Why this task is needed

CrowdCast uses one configuration source so that pipeline stages share the
same paths and experiment assumptions. Centralizing these values avoids
silently changing a hyperparameter or threshold in only one script.

## 3. What I implemented

Added the complete architecture-defined default configuration. It contains
paths, six configured months, cleaning limits, 18-zone tier counts, the
chronological split fractions, 168-hour windows, three quantiles, model
settings, training settings, evaluation settings, fleet assumptions, and E2
lookback values.

### File-by-file explanation

#### `config/default.yaml`

- **Responsibility:** Define the default paths and all configurable pipeline
  values for a full run.
- **Changes:** Added all sections and keys from `ARCHITECTURE.md` §3.
- **How it works:** YAML maps nested names such as `train.lr` and
  `windows.lookback` to values that the future configuration loader will
  return as a dictionary.
- **Why this design:** A single configuration contract keeps ingestion,
  feature construction, training, evaluation, and fleet estimation aligned.
- **Connections:** Future `src/config.py` will load it; each pipeline script
  will pass the relevant sections to its stage.

## 4. Architecture and data flow

This task creates configuration input; it does not read data or generate
artifacts. The future relationship is:

`config/default.yaml → load_config → ingestion/features/training/evaluation/app`

The six-month list controls raw input discovery. The paths control where
processed tables, checkpoints, metrics, and dashboard artifacts are stored.

## 5. Key technical decisions

| Decision | Reason | Alternative considered | Trade-off / consequence |
|---|---|---|---|
| Use the exact architecture-defined key hierarchy | Keeps all later modules aligned with the documented interfaces | Not considered | Future code must preserve these names unless an approved change is made |
| Use 18 selected zones by default | Six high, six medium, and six low zones satisfy the documented 15–20-zone objective | Not considered | The available dataset must contain enough eligible zones |
| Use 168 hours and six targets by default | Matches the primary experiment and six-hour forecast requirement | 24-hour lookback is retained only under `experiments.lookbacks` for E2 | Longer windows require more memory and computation |

## 6. Deep learning / data-science explanation

- **Concepts used:** Configuration-driven experimentation and reproducibility.
- **Inputs and targets:** The configuration declares the future data inputs,
  six-hour target horizon, three quantiles, and model/training settings; it
  does not contain observations or targets itself.
- **Math or loss function:** The quantile values `[0.1, 0.5, 0.9]` identify
  P10, P50, and P90; the loss is implemented in a later task.
- **Training/evaluation implications:** The same values will be used by both
  LSTM and GRU runs, supporting a fair comparison.
- **Leakage and reproducibility safeguards:** The configuration declares
  chronological fractions, train-only processing requirements remain in the
  architecture, and the seed list is `[0, 1, 2]`.
