### Why this task is needed

Neural networks train more reliably when demand is in a stable numeric scale.
Using validation or test rows to calculate that scale would leak future
information into training.

### Expected files

- `src/features/scaling.py`
- `docs/reports/M2-T3.md`

## 3. What I implemented

### `fit_zone_stats`

Fits the architecture-defined `zone_stats` structure from only rows inside
the inclusive train range:

- `mean_log`: mean of `log1p(pickups)`.
- `std_log`: population standard deviation of `log1p(pickups)`.
- `peak_threshold`: configured percentile of raw train pickups.

It raises an explicit error when a zone has zero log-demand variation.

### `apply_scaling`

Adds a `z_pickups` column using:

```text
(log1p(pickups) - mean_log) / std_log
```

It fails if a row has no corresponding fitted zone statistics.

### `compute_busy_time`

Produces 24 rows per train-period zone. Each value is a pickup-weighted mean
of hourly mean trip durations. Missing zone-hour values fall back to the
zone's overall train mean, then the global train mean.

## 4. Architecture and data flow

```text
hourly_selected.parquet + splits.json
    ├── fit_zone_stats → zone_stats.json-compatible mapping
    └── compute_busy_time → busy_time.parquet-compatible DataFrame
```

The functions do not write files; the feature-building CLI will own artifact
serialization.

### Explain it simply

The training period teaches us the normal scale of each zone. We use that
knowledge to express demand as “how far above or below normal” it is. We do
not let future data define what normal means.

## 7. Deviations and risks

- No PRD or architecture deviations.
- Population standard deviation is used for deterministic feature scaling;
  the architecture specifies the statistic but does not state a `ddof`.
- Busy-time calculation requires at least one valid weighted duration in the
  training data to provide the final global fallback.
