## 3. What I implemented

Added a minimal override file. It changes only the values required by the
task; all paths, window settings, model settings, evaluation settings, fleet
settings, and other defaults are inherited from `config/default.yaml` by the
future configuration loader.

### File-by-file explanation

#### `config/smoke.yaml`

- **Responsibility:** Define reduced settings for fast smoke validation.
- **Changes:** Uses January 2026, selects 2 high-volume, 2 medium-volume, and
  2 low-volume zones, sets two epochs, and sets the seed list to `[0]`.
- **How it works:** The future `load_config` implementation will merge these
  nested values over the full-run configuration.
- **Why this design:** Keeping only overrides makes the relationship between
  the full and smoke configurations explicit and avoids duplicating defaults.
- **Connections:** Future smoke commands will pass this file to each stage.

## 4. Architecture and data flow

No Parquet rows were loaded, no windows were built, and no model was trained.

## 5. Key technical decisions

| Decision | Reason | Alternative considered | Trade-off / consequence |
|---|---|---|---|
| Use January 2026 for the one-month smoke run | It is the first month in the selected current data period and is present locally | Use another configured month; not needed | The smoke result is not representative of the full eight-month experiment |
| Store only overrides | Prevents configuration drift between full and smoke runs | Duplicate the entire default file; not considered | Correct merge behavior is required from `load_config` |
| Use 2/2/2 zone tiers | Matches the task plan's six-zone smoke requirement | Uneven allocation; not considered | The data must contain enough eligible zones in each tier |
