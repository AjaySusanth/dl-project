## 2. Pre-coding briefing

### What I planned to do

Compute inclusive chronological train, validation, and test boundaries from
the unique hourly timeline and configured split fractions. The function will
return ISO strings and validate that the fractions and resulting ranges are
usable.

### Why this task is needed

Time-series evaluation must simulate forecasting the future. Explicit
non-overlapping ranges prevent target values from crossing between train,
validation, and test.

### Expected files

- `src/features/splits.py` — split-boundary computation.
- `docs/reports/M2-T2.md` — this task report.

## 3. What I implemented

Added `compute_splits`, which parses timestamps, removes duplicate timeline
values, sorts them, calculates chronological boundary indices, and returns:

```python
{
    "train": [start_iso, end_iso],
    "val": [start_iso, end_iso],
    "test": [start_iso, end_iso],
}
```

The function rejects missing columns, invalid fractions, and timelines too
short to create three ranges.

### File-by-file explanation

#### `src/features/splits.py`

- **Responsibility:** Define chronological split boundaries.
- **Changes:** Added timestamp normalization, fraction validation, boundary
  calculation, and ISO serialization.
- **How it works:** The unique sorted timeline is indexed according to the
  cumulative train and train-plus-validation fractions.
- **Why this design:** Splits are based on time positions rather than random
  rows, preserving the forecasting direction.
- **Connections:** Later scaling and window-building tasks will use these
  boundaries to enforce train-only statistics and target containment.

## 4. Architecture and data flow

`hourly_selected.parquet + split.fractions → compute_splits → splits.json-compatible mapping`

This task returns the mapping but does not write `splits.json`; the feature
building CLI will own that side effect.

## 5. Key technical decisions

| Decision | Reason | Alternative considered | Trade-off / consequence |
|---|---|---|---|
| Split unique timestamps, not raw rows | Every zone shares the same temporal boundaries | Split DataFrame row counts; rejected | Requires a complete hourly timeline |
| Return inclusive endpoints | Matches the architecture schema | Half-open intervals; not considered | Callers must treat both saved endpoints as included |
| Serialize with `Timestamp.isoformat()` | Produces machine-readable ISO strings | Save pandas timestamps; not considered | Downstream code must parse strings back to timestamps |

## 6. Deep learning / data-science explanation

- **Concepts used:** Chronological time-series partitioning.
- **Inputs and targets:** The input is the hourly timeline; future target
  hours must remain in later partitions.
- **Math or loss function:** Boundary positions use configured cumulative
  fractions, approximately 70%, 85%, and 100% of the timeline.
- **Training/evaluation implications:** Random splits could let future demand
  patterns enter training and make metrics unrealistically optimistic.
- **Leakage and reproducibility safeguards:** Sorted unique timestamps and
  deterministic index boundaries make the split repeatable and chronological.

### Explain it simply

The split function draws three consecutive time boxes on the calendar:
training first, validation next, and test last. It does not shuffle the
hours, because the system must learn from the past and be judged on the future.
